## Automated smoke script

For the Production isolation portion, set `APP_BASE_URL=https://app.workcraftai.com`, `NEXT_PUBLIC_SUPABASE_URL` to the matching Production Supabase project URL, and `NEXT_PUBLIC_SUPABASE_PUBLISHABLE_KEY` to the matching public key. Provide dedicated Free and Pro test-account credentials in the untracked `.env.local`, then run `node --env-file=.env.local scripts/production-readiness-smoke.mjs` (Node 24 supports `--env-file`). It checks health, public pages, and basic accessibility markup, signs in to the two test accounts, checks Free/Pro cloud-AI access, and verifies estimate reads through Supabase REST and the app API. A dedicated disposable estimate with one private test photo also enables the owner-versus-other-account signed-URL checks. The Production path does not update or delete estimate records, send email, or create Stripe payments; it does create Auth sign-in activity and a short-lived private-media signed URL for the owner. Leave `WORKCRAFT_E2E_ALLOW_FIXTURE_MUTATIONS` unset for Production. The script's signed Stripe mutation checks are restricted to localhost or a branch Preview.

For authenticated checks, provide dedicated Free and Pro test-account credentials through `WORKCRAFT_E2E_FREE_EMAIL`, `WORKCRAFT_E2E_FREE_PASSWORD`, `WORKCRAFT_E2E_PRO_EMAIL`, and `WORKCRAFT_E2E_PRO_PASSWORD`. Set `WORKCRAFT_E2E_CROSS_ACCOUNT_ESTIMATE_ID` to the disposable estimate and `WORKCRAFT_E2E_ESTIMATE_OWNER` to `free` or `pro` to verify the owner can read it and the other account cannot. Attach a photo from the estimate editor before running to include the private Storage checks. Use fictitious customer details and do not click **Email client** for this isolation fixture.

Stripe webhook checks mutate a payment fixture and are disabled by default. Run them only against localhost or a `-git-` Vercel branch Preview with Stripe **test-mode** credentials, `WORKCRAFT_E2E_ALLOW_FIXTURE_MUTATIONS=1`, and a dedicated pending test payment identified by `WORKCRAFT_E2E_PAYMENT_ID` and `WORKCRAFT_E2E_CONNECT_ACCOUNT_ID`. The script also submits concurrent copies of a no-op event to verify one durable claim. Never point it at Production or a real payment. These direct signed requests test the handler; separately confirm that Stripe's Preview destination shows successful provider delivery attempts.

## Rollback

The webhook claim migration is additive and leaves the existing boolean claim RPC available for old deployments. It is applied to Production and Staging; the matching handler is deployed. If deployment rollback is needed, the prior route continues to use the existing RPC; leave the additive database function in place. Do not delete webhook idempotency records or user data as an ad hoc rollback. Restore a backup only for a verified data-integrity incident, after the restore process itself has been tested.
